# LLM Wiki Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the in-repo LLM wiki specified in `docs/superpowers/specs/2026-07-07-llm-wiki-design.md`: a skeleton (`docs/wiki/` + CLAUDE.md wiring) plus four carefully verified core pages.

**Architecture:** Pure documentation — markdown pages under `docs/wiki/`, indexed from `INDEX.md` and the project `CLAUDE.md`. No code changes, no tooling. Each core page is drafted from direct source reading, self-verified claim-by-claim, then validated by quizzing a fresh agent that has only the page as context.

**Tech Stack:** Markdown, git. The Agent tool (or a fresh Claude session) for acceptance quizzes.

## Global Constraints

- All work happens on the `llm-wiki` branch. Never commit to `v0.2.8-dev` or `main`.
- Markdown files only. No changes to Python source, `pyproject.toml`, or Sphinx docs.
- Every wiki page starts with the exact header block defined in Task 1, including a `Last verified` stamp (`git rev-parse --short HEAD` + `date +%F` at time of writing).
- LLM-first writing: dense factual prose; real symbol names and `path/to/file.py` anchors; invariants stated explicitly; no narrative padding or marketing language. Line length ≤ 100 characters.
- Stubs contain only the header plus a scope statement — never fabricated content.
- Core pages go to the user for review **one at a time**, before their commit. Do not batch.
- Every factual claim about the codebase must be verified against the actual source before the page is presented. Claims that cannot be verified (pure domain knowledge) must be internally consistent and flagged for user review.
- Note: the project `CLAUDE.md` is currently untracked. The Task 1 commit adds it in full (this branch is isolated from dev, per the user's request).

- [ ] **Step 2: Draft the page**

Use the canonical header block (Title: `Solver Architecture`; Purpose: `How gain terms, mappings, and the calibration graph fit together — read before touching quartical/gains/ or quartical/calibration/.`). Required sections and the claims each must establish (each claim cited to file, with symbol names — exact content comes from Step 1 reading):

1. `## The term abstraction` — what a "term" is; `TERM_TYPES` registry contents and how `solver.terms` names map to classes; the full contract a term package provides (class attributes, mapping methods, `solver = staticmethod(...)`, param names for parameterised terms; use `complex` and `delay` as the two worked examples).
2. `## Gain vs ParameterizedGain` — what the base class provides, what parameterisation changes (solve in param space, convert to gains), which existing terms use which.
3. `## Graph construction path` — `add_calibration_graph` → per-xds mappings → `construct_solver` → `solver_wrapper`, stating for each hop the actual function signature shape (inputs/outputs) and which file owns it.
4. `## Interval mappings` — what time/freq interval mappings ARE (array shapes, semantics), where built (`mapping.py` functions by name), where consumed (kernels), and the invariants (e.g. relationship between data chunks and solution intervals).
5. `## Numba kernel conventions` — the factory pattern in `factories.py`: what problem it solves (correlation-mode dispatch without runtime branching), how a kernel is structured, the flagging hooks from `general/flagging.py`.
6. `## Outputs` — what a solve produces per term (gain xds → zarr via `gains/datasets.py`), and residual/corrected-data outputs.
7. `## Adding a gain type` — concrete recipe distilled from the above: new package, registry entry, `gain_schema.yaml` exposure, per-type test in `testing/tests/gains/`.

**Files:**

- [ ] **Step 1: Ground the vocabulary in source**

- [ ] **Step 2: Draft the page**

Header (Title: `Domain Primer`; Purpose: `The radio-interferometry and optimisation background QuartiCal's code assumes — RIME, Jones chains, gain solving as complex NLLS.`). Required sections:

1. `## The RIME in one page` — visibilities as 2×2 coherencies corrupted by per-antenna Jones matrices; the measurement equation V_pq = J_p B_pq J_q^H (in the notation the codebase implies); which parts QuartiCal takes as given (model visibilities) and which it solves for (Jones terms).
2. `## Jones chains` — `solver.terms=['G','B',...]` as an ordered product of Jones matrices; why order matters (non-commuting 2×2 matrices); sky-side vs antenna-side placement; direction-dependent vs direction-independent terms and what changes computationally.
3. `## Gain solving as complex NLLS` — the residual being minimised; complex optimisation (Wirtinger calculus) in the CubiCal/QuartiCal lineage — cite the CubiCal papers (Kenyon et al. 2018; Smirnov & Tasse 2015) as the authoritative references; iteration structure (per-chunk, per-term alternating solves); solution intervals as the resolution/SNR trade-off.
4. `## Parameterised terms` — why delay/phase/TEC/rotation solve for physical parameters instead of raw complex gains (fewer DoF, physical smoothness across frequency, e.g. delay ⇒ phase linear in ν); how params convert to gains; consequences for interpolation.
5. `## Vocabulary map` — table: term name in config ↔ config section ↔ `TERM_TYPES` key ↔ `Gain` subclass ↔ on-disk zarr dataset; plus glossary lines for chunk, solution interval, mapping, direction, xds.
6. `## Pointers` — the existing user docs (`docs/source/gain_types.rst` etc.) and papers, for depth.

Physics/maths claims must be standard textbook material stated conservatively; anything
uncertain gets dropped or flagged `(verify)` for the user rather than guessed.

4. What is a solution interval, and what trade-off does it control?
